## 对话测试页 Markdown 渲染优化（llm-proxy-tk）
- 需求：对话页 AI 回复需按 Markdown 渲染，代码块可复制，整条回复可复制。
- 方案：静态资源本地化引入三方库（避免内网运行时依赖 CDN）：
  - `proxy/app/static/vendor/marked.min.js`（v12.0.2 UMD）
  - `proxy/app/static/vendor/highlight.min.js`（v11.9.0）
  - `proxy/app/static/vendor/purify.min.js`（DOMPurify 3.1.6，用于净化 marked 透传的原始 HTML，防 XSS）
- 改动：
  - `index.html`：在 app.js 前按序引入三个 vendor 脚本。
  - `app.js`：
    - 新增 `renderMarkdown()`（marked parse → DOMPurify sanitize → 遍历 pre/code 包一层 `.code-block`+`.code-head`+语言标签+复制按钮，hljs 高亮）。
    - `addChatMsg("assistant")` 改为结构化气泡：`.chat-bubble-md` = 工具条（整条复制按钮）+ `.chat-bubble-content`；提供 `bubble.setMsg(text,{raw})`，raw=true 走纯文本降级（调试/错误），否则渲染 Markdown。用户气泡保持原纯文本逻辑。
    - `sendChat`/`readRawStream`/`readChatStream` 改用 `setMsg`；流式渲染 40ms 限速，结束时强制刷新。
    - 复制按钮通过 `#chat-messages` 容器事件委托（`handleChatClick`）+ `copyToClipboard()`（clipboard API，失败回退 execCommand），兼容流式重渲染。
  - `styles.css`：新增 markdown 排版（标题/列表/表格/引用/行内代码等）、`.code-block` 深色代码块容器（GitHub Dark 风格 hljs 配色，深浅主题下都协调）、复制按钮样式。
- 验证：已用无头 Chrome 对测试 HTML 做 DOM 断言（h3、行内 code、a 链接、code-block、copy-code-btn、hljs 高亮类均出现；onerror/script 注入被净化）。网关 9000 端口在跑，静态文件 200。
- 注意：`proxy/data/keys.db` 有 working copy 改动，与本任务无关，勿提交。

## 流式输出“半天没回复”修复
- 根因：非 raw 流式请求时助手气泡为空（首 token 到达前无任何反馈）；且 `readChatStream` 每 40ms 全量 Markdown 渲染 + hljs 高亮，内容一长主线程被 O(n²) 同步重排占死，读取停摆，表现为无输出/挤牙膏。
- 修复（app.js）：
  - `sendChat`：非 raw 时先 `setMsg("正在思考…")` 占位，首 token 到达即替换。
  - `renderMarkdown(md, opts)`：新增 `opts.light`，流式中间态只做 parse+sanitize，跳过 hljs 高亮与代码块包装。
  - `readChatStream` 重写：收到首个内容 token 立即渲染；后续按累计长度自适应渲染间隔（<1k:60ms，<4k:120ms，<10k:200ms，更长:320ms）做 light 渲染；流结束清定时器并完整渲染一次（高亮+复制按钮）。
- 验证：临时复制 index.html 拦截 /v1/chat/completions 喂本地 SSE 分片流，无头 Chrome 断言 9 项全 PASS（h1/strong/table/code-block/copy-btn/hljs 类/占位替换/_rawText 完整/raw 未误用），无 console 报错。测试文件已删。

## cc-switch 通过 llm-proxy-tk 网关接入 Ollama/qwen3:8b
- 用户意图：在 cc-switch 中为 Claude Code 新增本地 qwen3:8b 供应商，并希望流量走 llm-proxy-tk 网关（9000）再到 Ollama（11434），以获得 sk 鉴权和用量统计。
- 关键前提：Ollama 只支持 OpenAI 方言（`/v1/chat/completions`），Claude Code 默认说 Anthropic 方言（`/v1/messages`），中间必须有人翻译。cc-switch 新版提供“本地路由/代理”功能，打开后由 cc-switch 完成 Anthropic↔OpenAI 翻译，再转发到配置的供应商 Base URL。
- cc-switch JSON 配置示例（替代现有 hrgk-deepseek 的应用配置）：
  ```json
  {
    "codemossProviderId": "qwen3-local",
    "env": {
      "ANTHROPIC_BASE_URL": "http://127.0.0.1:9000",
      "ANTHROPIC_AUTH_TOKEN": "sk-你在网关后台发的密钥",
      "ANTHROPIC_MODEL": "qwen3:8b",
      "ANTHROPIC_DEFAULT_HAIKU_MODEL": "qwen3:8b",
      "ANTHROPIC_DEFAULT_SONNET_MODEL": "qwen3:8b",
      "ANTHROPIC_DEFAULT_OPUS_MODEL": "qwen3:8b",
      "CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC": "1"
    },
    "extraKnownMarketplaces": {
      "anthropic-agent-skills": {
        "source": {
          "repo": "anthropics/skills",
          "source": "github"
        }
      }
    },
    "theme": "dark"
  }
  ```
- 启用步骤：把 JSON 贴到 cc-switch「编辑应用配置」→ 供应商名称改为 `qwen3-local` → 打开 cc-switch 设置 → 高级 → 本地路由（代理）开关 → 启用该供应商 → 重开 Claude Code → `/model` 选 qwen3:8b。
- 验证命令：
  ```bash
  curl http://127.0.0.1:9000/v1/chat/completions \
    -H "Authorization: Bearer sk-你的密钥" \
    -H "Content-Type: application/json" \
    -d '{"model":"qwen3:8b","messages":[{"role":"user","content":"hi"}]}'
  ```
- 备选：若 cc-switch 版本无本地路由功能，可额外部署 LiteLLM 作为翻译层，指向 `http://127.0.0.1:4000`（或其他端口），cc-switch 中 ANTHROPIC_BASE_URL 改为该地址。
- 安全收益：网关层实现了 sk 密钥隔离、可吊销/过期、用量统计，后续接入云 API 也只需在网关后台加新上游。

## qwen3 思考模式导致 Claude Code workflow 循环 → 自制 qwen3:8b-nothink 解决
- 现象：IDEA 中切到 qwen3:8b 后对话一直"分析 → workflow → 中断 → 重新分析"，循环不停。
- 根因（实测确认，Ollama 0.33.2）：
  1. qwen3 默认开"思考模式"，token 全花在内部 reasoning；OpenAI 兼容接口 `/v1/chat/completions` 下返回的 `content` 为空、`reasoning` 字段一堆碎碎念，且 **OpenAI 兼容接口不认 `think:false`**（原生 `/api/chat` 认）。
  2. content 为空 → Claude Code/cc-switch 翻译层拿到空回复 → 判定失败 → 重试循环。
  3. 另发现本机 `size_vram:0`，qwen3:8b 是纯 CPU 推理，8B 思考一次 18~78s，加剧超时重试。
- 修复：在 Ollama 用 `from` + 顶层 `template` 字段创建自定义模型 `qwen3:8b-nothink`，改 chat 模板强制禁思考：
  - 最后一条 user 消息守卫 `{{- if and $.IsThinkSet (eq $i $lastUserIdx) }}` → `{{- if eq $i $lastUserIdx }}`（默认走 no_think 分支）。
  - assistant 开头空 think 块守卫 `{{ if and $.IsThinkSet (not $.Think) -}}` → `{{ if true -}}`。**关键：qwen3 真正禁思考信号是 assistant 开头的空 `<think>\n\n</think>` 标记**，不是用户消息里的 /no_think 文本。
  - 创建 API：`POST /api/create {"model":"qwen3:8b-nothink","from":"qwen3:8b","template":"<修改后模板>"}`（Ollama 0.33.2 的 create 不认 `modelfile`/`path` 字段，只认 `from`+顶层 `template`）。
- 验证结果（qwen3:8b-nothink，OpenAI 兼容接口 + 网关 9000 全链路）：普通对话 content 正常、1.1s；工具调用返回标准 `tool_calls`（list_files {"path":"/"}）、3s、无 reasoning。
- 待办：cc-switch 供应商 JSON 里 4 处模型名（ANTHROPIC_MODEL + haiku/sonnet/opus 映射）全部从 `qwen3:8b` 改为 `qwen3:8b-nothink`，重启 Claude Code 生效。
- 性能备注：CPU 推理 8B 仅 ~5-15 token/s，agent 多轮仍偏慢；要流畅建议上 GPU 或用 qwen3:4b/qwen2.5-coder 系列小模型。模型创建方法可复用（`from`+`template`，见上文 API）。
- 追加对照（用户手动 curl 原始 qwen3:8b + 工具请求）：单轮工具调用能成功返回 `tool_calls`（list_files {"path":"./"}），但 completion_tokens=441、其中 400+ 是 reasoning，content 空；同请求 qwen3:8b-nothink completion_tokens=19、无 reasoning、6.4s。结论：原始模型单轮简单场景可能成功，但多轮 agent 长上下文下 reasoning 易挤掉 tool_calls/content 导致循环，仍必须用 nothink 模型。
- **最终结论（18:00）**：用户把 cc-switch 模型名改成 qwen3:8b-nothink 后（状态栏确认生效，`ollama ps` 已加载 nothink），IDEA agent/workflow 模式下仍循环/极慢（13min+ 单轮）。根因定位为双重：① 8B 纯 CPU（~5-15 tok/s）跑复杂 agent 多轮工作流是数量级瓶颈；② qwen3:8b 规划能力不足——插件"自动模式"把简单请求（写冒泡排序）包装成复杂 workflow（Write file.json/confirmed_bugs.json/workflow.js + Workflow 工具），模型执行 Workflow 失败→插件重试→循环。单轮 tool_call 格式正确 ≠ 能稳定跑完整 agent loop。
- 建议方案：agent 编程走云端模型（原 hrgk-deepseek/DeepSeek），本地 qwen3:8b-nothink 只做简单对话/补全；或升级 14B+/GPU。已产出面向公众号的深度复盘文章。
