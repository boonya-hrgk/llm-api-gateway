## DeepSeek anthropic 端点误配为网关上游 → 对话 404
- 现象：上游管理新增 deepseek，基础地址填 `https://api.deepseek.com/anthropic`，网关内置对话测试请求 404。
- 根因：llm-proxy-tk 是 **OpenAI 方言透传**网关，`proxy/app/proxy.py` 的 `_target_url` 固定把请求拼成 `{上游base_url}/v1/{path}`。收到 `/v1/chat/completions` 后拼成 `https://api.deepseek.com/anthropic/v1/chat/completions`——而 `/anthropic` 端点只支持 Anthropic Messages 协议（POST `/v1/messages`、`x-api-key` 头、`anthropic-version` 头），没有 OpenAI 风格的 `/v1/chat/completions` 路由 → 404。
- 修复：上游基础地址改为 OpenAI 兼容根地址 **`https://api.deepseek.com`**（不带 `/v1`、不带 `/anthropic`，因为网关会自动拼 `/v1/chat/completions`）；对话测试 model 填 `deepseek-chat` / `deepseek-reasoner`。
- 注意：网关 health 探活是 `{base_url}/health`，DeepSeek 没有该端点，健康检查可能显示 502/不可达，但**不影响实际对话转发**，属预期噪音。
- 要点：llm-proxy-tk 只能接 OpenAI 兼容上游；Anthropic 方言的端点（api.deepseek.com/anthropic）应通过 cc-switch 之类带协议翻译的层使用，不能直接作为本网关上游。

## 流式翻译层输出重复修复（compat.py，未跟踪新文件）
- 现象：OpenAI→Anthropic / Anthropic→OpenAI 两条流式转换链路输出事件整体翻倍（message_start/stop、content_block_start/stop 各出现 2 次）。
- 根因：`OpenAIStreamToAnthropic.feed/flush` 与 `AnthropicStreamToOpenAI.feed/flush` 都直接 `return b"".join(self._output)` 且**从不消费** `_output`。而 `proxy/app/proxy.py` 的 `translated_iter` 是「每 feed 一块就 yield 返回值 + flush 再 yield 一次」的增量消费契约 → 后续每个上游 chunk 的返回值都重复携带此前全部历史事件，flush 又全量补一遍。首次测试把整段 SSE 一次喂入再 flush，两份全量拼在一起正好看出完整翻倍。
- 修复：两转换器新增 `_drain()`（返回 `_output` 当前拼接值后 `clear()`），feed/flush 末尾统一走 `_drain()`。同时给 `AnthropicStreamToOpenAI` 补 `_done` 标志（其 flush 原本靠扫描 `_output` 中是否含 `data: [DONE]` 判断是否已收尾——清空 `_output` 后该判据失效，必须换成标志位）；`_finish` 顶部加 `if self._done: return`。
- 验证：①OpenAI 流单次全量 vs 7 字节步长分块喂入 → 事件序列完全一致，message_start=1 / stop=1 / block_start=2 / stop=2 / delta=5；②Anthropic 流含 message_stop 分块喂入 + flush → 4 chunk + 1 [DONE] 无重复；缺 message_stop 断连场景 flush 兜底同样只补一次；空流 flush 返回空不产垃圾。
- 契约要点：这两个转换器的 `feed()/flush()` 返回**本批次新增**字节，调用方负责拼接，不可假设返回全量历史。

## DeepSeek anthropic 上游对话测试 502 ConnectError + 非流式响应翻译方向写反
- 用户场景：key 6 绑定 deepseek 上游（base `https://api.deepseek.com/anthropic`、protocol=anthropic、models deepseek-v4-flash/pro），对话测试页 OpenAI 方言请求 `POST /v1/chat/completions` → 502 `{"detail":"上游请求失败: ConnectError"}`。
- 根因 A（连接）：网关跑在 **pyenv 3.10.0**，其 httpx `AsyncClient()` 默认 `trust_env=True` 时本机**所有 HTTPS 出站必然 ConnectError('')**（deepseek/baidu 都失败、HTTP 正常）；`trust_env=False` 直连正常（401/200）。3.14 解释器无此问题。proxy.py 三处 httpx 客户端（`_stream_upstream`/`_forward_translated`/health）都没设 trust_env → 撞坑。
- 根因 B（翻译方向）：修好连接后返回 200 但 body 是 `type:"message"` + `content:[]` + usage 全 0——`_forward_translated` 非流式正常响应分支里两个方向的函数名写反：entry=openai/exit=anthropic 时把上游 Anthropic 响应喂给了 `openai_to_anthropic_resp`（它按 choices 取数，拿到 anthropic 形状→产出空内容假响应）。流式分支和错误分支方向是对的，所以之前流式 e2e 没暴露。
- 修复（proxy.py）：
  1. 三处 `httpx.AsyncClient(...)` 全部加 `trust_env=False`（注释说明 pyenv3.10 复现结论）；
  2. 非流式正常响应映射改为：entry anthropic&exit openai → `openai_to_anthropic_resp`；entry openai&exit anthropic → `anthropic_to_openai_resp`；
  3. 新增 `_upstream_error_detail(exc)`，502 detail 带上底层异常文本（截断 300），替代原来只有类名的写法（4 处调用点替换）。
- 验证（9003 临时实例 + 正式库副本 + 真实 DeepSeek，pyenv 3.10 跑）：stream=false 返回标准 OpenAI chat.completion（content 正常、usage 有值）；stream=true 返回 OpenAI SSE 分块 + `[DONE]`；非法模型返回 OpenAI 形状错误体且错误文案确认合法模型即 `deepseek-v4-pro`/`deepseek-v4-flash`（另有 -vision-exp）。临时实例与副本已清理。
- 注意：**正式服务 9000（PID 40648）仍需重启**才加载 proxy.py 修复。DeepSeek anthropic 端点探活仍会 502（无 /health），属预期噪音。
